# 测试计划怎么定

用风险矩阵定用例量级与环境；开测/收测写成可观察构建事实，禁止门禁/放行腔。

## 何时用

- 迭代开测，范围与完成定义不清
- 要区分 Logic 自动证据与 Visual/Feel 手工证据
- 弱网/兼容热点要进计划并能量化用例量级

## 怎么做

### 1. 冻范围并建风险矩阵

1. 从迭代故事与 AC 加载；无则与用户冻结合/不含；缺 AC 列缺口不发明。
2. 计划头写死：迭代名 | 含故事 ID | 不含邻接系统。
3. 风险矩阵列：`story_id`、面积、似然、影响、风险分、热点标签；表引擎写入。
4. 热点强制行：弱网、存档迁移、支付、兼容 N-1、低端机——无则写接受风险理由。
5. 检查含/不含可勾选；高风险无 AC 则补 AC 或降为不含。

**做到**：含/不含与风险矩阵可勾选；热点行齐全或有接受理由。

### 2. 风险分→用例量级与证据类型

1. 写明换算规则：高/中/低风险对应测法条数量级；Config 抽检另列。
2. 按 Logic/Integration/Visual/Feel 分流；混合故事拆开自动证据与手工证据。
3. Feel 写可观察证据类型；Visual 约定分辨率与机型。
4. 每故事一行：Type | 目标用例量级 | 证据形态 | 路径槽或观察点。
5. 人力不够则回步骤 1 砍不含或降密度；禁止门禁腔表述。

**做到**：每故事有 Type、用例量级、证据形态。

### 3. 环境与自动/手工/冒烟范围

1. 环境清单：`env_id`、构建 SHA 槽、设备或 OS、表版本、账号档；主环境+热点环境。
2. Logic 写路径槽与边界点名；Smoke 写成可勾选短句（冷启/主机制/烫手点/存档）。
3. 自动化候选只标 ROI 粗档，细节交 `case-automation-map`。
4. 每 AC 至少一条对应测法意向；缺构建号槽标开测阻塞直至可填。
5. 检查三类范围非空且环境可指。

**做到**：自动/手工/冒烟范围非空；环境清单可指。

### 4. 开测/收测可观察条件

1. 开测条件写成构建事实：SHA 已出包、约定冒烟已跑或阻断已挂单、表版本匹配、计划头已冻。
2. 收测条件必须可核对：计划内 P0 执行率、**遗留致命缺陷列表**、**豁免单号与回补**、证据包路径。
3. 非目标与已知风险显式列出；结论选项留给用户拍板，本文件只给可核对事实。
4. 风险最高三块写加测理由一行。
5. 检查条件可观察、无「感觉能过」；不合格回本步改写成事实句。

**做到**：开测/收测条件为可观察构建事实；遗留致命与豁免/回补可引用。

## 做到

- 含/不含与风险矩阵可勾选；热点行齐全或有接受理由
- 每故事有 Type、用例量级、证据形态；环境清单可指
- 开测/收测条件为可观察构建事实；自动/手工/冒烟范围非空

## 失败回哪一步

- 含/不含空、热点无理由、发明 AC → 回步骤 1
- 用例量级超人力未砍范围 → 回步骤 2（或回 1）
- 环境无 SHA 槽、三类范围空 → 回步骤 3
- 收测缺遗留致命列表/豁免单号、形容词进出 → 回步骤 4

## 边界

- 不做：逐条用例 GWT 正文；自动化框架编码；发版商务签字与商店提审操作；性能采样原始数据全文

## 工具锚

- CI 流水线配置（`.yaml` / workflow）与冒烟命令日志
- 失败用例名与复现步骤写入 `.harness/artifacts/`
- `verify-report.json` 引用本批日志路径
