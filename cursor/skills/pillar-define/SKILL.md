# 体验支柱怎么定

## 何时用

- 立项或大改方向需定支柱，决策缺否决标准
- 职种间对「什么重要」不一致，功能提案无法对齐体验
- 复盘发现现有支柱无法用试玩条目检验

## 怎么做

### 1. 锚定目标美学与非目标

**做**
1. 打开 `design/gdd/game-concept.md`（或等价愿景）与支柱模板；用 `rg -n "fantasy|愿景|核心体验" design/gdd` 抽出硬承诺句，冲突并列请用户裁，不静默合并。美学排名写入 sheet `pillars_aesthetics.csv`（列 Rank|Aesthetic|DeliverySystemId）。
2. 写目标玩家感受句（Challenge/Fantasy/Discovery 等 MDA 美学排名前 2～3）；每条附「交付机制」字段（具体系统名槽，非空形容词）。
3. 写 ≥3 条非目标（Anti-pillars）：必须是团队可能真想做的东西（如「NOT 开放世界」），并注明会牺牲哪条美学。
4. 在功能 backlog / 里程碑板（Jira/Linear/Notion board）导出本季候选 feature id 到 `pillars_feature_triage.csv`，列 `feature_id|aesthetic_link|triage(serve|unrelated|conflict)`；无关项不得进必须包。用板过滤器或 CSV 勾选复核。
5. 若艺术/技术预算与美学冲突：在美学锚写「理想 | 约束 | 本版选用」三栏；本版只按选用开工。
6. 失败→回本步：美学句无法映射到任一系统名槽，或非目标写不出可砍功能类型——改句再往下。

**做到**：美学排名表有交付机制槽；非目标 ≥3 且各绑可砍功能类型；候选 feature 三态表可指 id。

### 2. 起草可检验支柱 + 玩法 checklist

**做**
1. 写 3～5 条支柱：每条 = 一句可证伪承诺 + Design Test（「争论 X vs Y 时选 __」）+ 跨职种含义各一行（设计/美术/音频/叙事/工程）。
2. 每条支柱附 **玩法 checklist ≥3 条**：可在试玩中勾选的观察项（例：局内 10 分钟内玩家是否主动使用耐心机制 ≥2 次——具体阈值向用户索取，不编造）。工具面：`playtest_checklist.csv` + stopwatch + OBS/引擎录像时间码；勾选结果写 PASS/FAIL+时间码。
3. 用 `rg` 扫空心词（好玩|深度|品质|沉浸）出现在承诺句中则整句重写；空心句进删除清单防回潮。
4. 给 2 套支柱组合（更硬核 / 更宽松）+ 对产能与否决面的利弊；用户锁定主集后写冻结日期。
5. 每条支柱必须能绑定 ≥1 个现有或拟做 feature id 作为「正例」与 ≥1 个「反例」（见下一步）；绑不上则改承诺句。
6. 失败→回步骤 1：checklist 只能写成「感觉对了」或无法用 stopwatch/录像点验证——先改美学交付机制再重写支柱。

**做到**：主集 3～5 条；每条有 Design Test、跨职种行、≥3 条可勾试玩 checklist；冻结日期已写。

### 3. 反例绑 feature id + 否决演练

**做**
1. 打开功能 backlog / systems-index；为每条支柱写 ≥2 个反例：格式 `feature_id | 为何违反本支柱 | 否决结论（砍/改约束/移出本里程碑）`。
2. 正例同样绑 id：`feature_id | 服务哪条 checklist 项`；正反例不得共用同一 id。
3. 在里程碑板建「Pillar Reject」标签或自定义字段；把本轮否决演练的假想/真实提案记入卡片评论：支柱 ID、结论、日期。同步写 `pillars_rejects.csv`（feature_id|pillar_id|verdict|date）便于 `rg`。
4. 演练 ≥2 个功能类型（系统型 + 内容型）；若任一支柱否决不了任何提案，回步骤 2 加约束词。
5. 用表格输出：PillarID | 承诺 | checklist | 正例 feature_ids | 反例 feature_ids。
6. 失败→回步骤 2：反例只能写品类空想、绑不到 backlog id——收窄承诺或补 backlog 条目后再绑。

**做到**：每支柱 ≥2 反例均含真实/拟做 feature id；里程碑板有否决记录可链；演练覆盖系统+内容两类。

### 4. 张力优先级写入里程碑板

**做**
1. 两两支柱标张力（同时难满足处）与优先序表：冲突时听高优先级；写「若冲突则听 P_x」句式。
2. 在里程碑板（或 ADR/`promote-adr`）建冲突决议卡：字段 = 冲突支柱对、争议 feature id、适用优先规则、决议、Owner、日期。
3. 抽 1 个真实争议（或构造贴合本项目的争议）走完决议卡；决议结果贴回 feature 卡与支柱文档互链。
4. 变更规则：改一条支柱必须重跑张力表 + 否决演练 + 更新板字段；升版本号。
5. 发布一页支柱卡路径（`design/gdd/game-pillars.md`）；`systems-index` / feature-gdd 文首引用该路径；旧支柱文档标废弃指针。
6. 失败→回步骤 3：冲突卡写不出适用 feature id，或优先序无法裁决演练案——调整优先序或反例后再冻结。

**做到**：优先序表可裁决；≥1 张冲突决议卡含 feature id；支柱卡路径可被下游引用且有版本/冻结日。

下一步常接：`systems-index-map`；功能提案用支柱否决；试玩批评 `experience-critique`。

## 细则

### A. 写法
1. 3～5 条；每条：陈述 + 像 + 不像 + 可观察检验。
2. 互斥目标拆条或写生效条件，禁止空喊「既 A 又反 A」。
3. 版本号与生效里程碑；旧版 Deprecated 指针。
4. 否决清单：至少 5 个「看起来酷但不做」例子。
5. 用户批准前不宣称全组生效。

### B. 引用
1. GDD/关卡/商业文档文首引用 `pillar_version`。
2. 评审时逐条勾「支持/无关/违背」。
3. 违背项必须改设计或升 scope-cut。
4. 信号：支柱无法否决任何功能=写失败。
5. 检查体量：维持并作回归。
