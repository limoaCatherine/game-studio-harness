# 更新说明怎么起草

## 何时用

- 版本/热更需要玩家说明；变更日志要转成对外语言
- 要分亮点/调整/修复/已知问题；经济/平衡削弱需诚实表述
- 已预告内容变更或砍掉需沟通口径

## 怎么做

### 1. 收集变更集并核对合入

1. 跑 `git log --oneline <prev_tag>..HEAD` 与 `git diff --stat <prev_tag>..HEAD`；导出提交列表到 `release/<ver>/commits.txt`，表变更另存 `tables.diff`。
2. 收表 diff（`tunable-table-diff` 报告）、任务单导出、`scope-cut-decision` 决议、活动开关列表。
3. 每条写入变更表：`id|system|player_visible|risk|source_ref|merge_sha_or_flag|status(merged|pending)`；表写入走 `excel-com-write`。
4. 纯内部项（重构/日志）移 `dev_notes`；核对 CI 产物/标签是否含 merge_sha——未合入保持 pending，用「计划中」语气。
5. 对照 `liveops-calendar` 与商店预告文案：已预告未上项单列沟通策略（延期/取消/替代）+负责人。
6. 经济/付费/削弱打 `sensitive=true`；向用户确认语气档与多语言是否同步。

**做到**：变更表每行有 source_ref；merged/pending 已分；预告差策略表非空（若有差）。

### 2. 分类转写玩家语言

1. 分类桶：亮点、新内容、玩法调整、品质、修复、性能、已知问题、活服。
2. 转写只说玩家影响，不写票号；数值改对照表 diff 写明增强/削弱方向（↑/↓）。
3. 重大削弱直说影响面与原因方向（公平/性能/经济健康）；削弱进「玩法调整」桶，不塞进「修复」。
4. 新系统用「能做什么」句；术语 `rg` 对照命名规范，用玩家可见名。
5. 活动项写时间窗（日历日）+ 入口 UI 键名；与实机入口字符串一致。
6. L10n：避开难译双关；占位符保持命名；超长句按 `copy-pass` 压缩。

**做到**：分类稿无票号；sensitive 削弱已直说；时间窗与入口键可在包内对上。

### 3. 亮点、已知问题、口径冻结

1. 选 3～5 条亮点（玩家最先感知）；其余进分类。
2. 已知问题写：现象 + 规避步骤；无规避写「调查中」+ 反馈入口 URL/键。
3. 标「事实冻结点」时间；之后改数须同步改说明。客服话术文档粘贴同一削弱/故障句。
4. 补偿：仅当邮件/领取配置已存在（`reward-mail-check` 通过）才写入领取方式。
5. 法律/合规句单独块；输出 `release/<ver>/stub.md` 交社区/本地化润色。

**做到**：stub 文件存在；亮点 3～5；已知问题含规避或调查中；客服同句；补偿有配置证据。

### 4. 包内抽检、渠道、勘误

1. 抽 ≥3 条高风险（含全部 sensitive）到包内验证：入口可点、数值方向可感；在引擎/真机打开对应 UI，对照表 `sheet.col` 抽样；记验证构建号到 `release/<ver>/smoke.csv`。
2. 用浏览器打开公告链接/商店页；二维码扫码或解码校验；坏链当场修。结果记 `channels_check.csv`。
3. 渠道勾选表：游戏内公告、商店页、社区、邮件——漏渠道则补发或显式「仅游戏内」。
4. 写勘误权责：谁可改说明、如何标「更正」、同步哪些渠道；热更改表启动 `hotfix_notes_patch` 清单。
5. 归档 `stub.md` vs 终稿 diff；发布后若表再变，24h 内补丁说明。包内验证失败则从 stub 删除或改回 pending。

**做到**：抽检记录含构建号与 PASS；渠道覆盖清楚；勘误与热更同步规则落盘。

## 做到

- 变更皆有来源；pending 未冒充已上
- 分类完整；敏感削弱语气已审
- 亮点 3～5；已知问题含规避或调查中
- 预告差有策略；包内抽检通过；渠道与勘误/热更同步流程明确

## 失败回哪一步

- pending 出现在「已上」草稿 → 回步骤 1
- 削弱方向与表 diff 符号相反、票号堆砌 → 回步骤 2（先对 diff）
- 亮点含 pending、补偿无配置却承诺 → 回步骤 3
- 包内验证失败仍上线 → 回步骤 3 删/改 pending 再抽检（步骤 4）

下一步常接：定稿 `copy-pass`；公告日对齐 `liveops-calendar`。
