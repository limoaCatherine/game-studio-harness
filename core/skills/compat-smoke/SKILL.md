# 兼容性冒烟怎么跑

## 何时用

- 大版本或热更后要验旧档/旧协议
- 协议加删字段、资源补丁变更
- 需明确不支持组合的用户可见行为
- 防迁移失败覆盖好档

## 怎么做

### 1. 定兼容矩阵

1. 矩阵维：客户端×服务器×存档×资源；必测格至少 N/N 与 N-1 存档进 N；格编号 C1…；期望可玩/提示升级/拒绝。
2. 向用户索取最低仍支持旧版本；热更轨与全量轨分列；资源版本与客户端解耦时单独一维。
3. 不支持组合也要有期望行为；冻结本轮必测格清单；矩阵表走 `excel-com-write` 若用 xlsx。
4. 每格写测法锚：旧档路径 / mock 协议脚本 / 缺补丁包名。

**做到**：必测格与期望行为冻结成表；可指格子 ID；测法锚可执行。

### 2. 升级路径实测

1. 旧档进新端：抽检任务状态/货币/装备次数；失败隔离坏档并保留好档；迁移日志 from→to+原因码。
2. 半初始化检查清单：临时档、下载缓存、断点续传目录；失败后应可手动清理并写进缺陷。
3. 旧端对新服：支持则测登录主路径，不支持则友好提示；旧档样例检入 `tests/fixtures/saves/`。
4. 升级后对照 `save-schema-pass` 抽检字段列表；半写残留开缺陷。

**做到**：旧→新升级路径有实测记录；失败隔离可验证（不影响好档）。

### 3. 协议与资源失败

1. 模拟过旧/未知字段/缺补丁：提示或拒绝、不崩、不静默脏写；文案含更新指引；行为与 `server-api-contract` 一致。
2. 未知字段：应忽略或拒，与契约一致；缺补丁不静默用错资产。
3. 用抓包工具或 mock client 改字段复现；记录用户可见文案与错误码。
4. 失败路径进手工批与能自动的契约测；步骤写入可回归清单。

**做到**：失败路径可读错误码/提示且无崩溃脏写；坏档不污染好档目录。

### 4. 写清支持范围

1. 支持范围表可对外复述；阻塞级（崩/脏写）与文案级分列开缺陷；与 `save-schema-pass`/`server-api-contract` 版本号交叉。
2. 结果绑定构建号存 `compat/<build>/matrix_results.md`；阻塞缺口未解则兼容结论保持未完成。
3. 对外一句最低版本+升级指引；支持范围表进发行说明草稿（可交 `release-notes-stub`）。

**做到**：支持范围表可对外引用（平台/版本/限制）；结论依据矩阵实测。

## 做到

- 必测格跑完；旧档升级行为符合设计
- 不支持组合有提示、无脏写、无崩溃；支持范围写清

## 失败回哪一步

- 只测最新对最新、期望未冻、缺最低旧版本 → 回步骤 1
- 迁移覆盖好档、半写缓存残留 → 回步骤 2
- 失败路径崩或静默脏写、与契约不一致 → 回步骤 3
- 阻塞缺口未开单却称兼容完成 → 回步骤 4

下一步常接：`save-schema-pass` / `server-api-contract`。
