# 技术决策怎么写成 ADR

## 何时用

- 引擎、协议、存储、工具链等选型要留可追溯记录
- 用户确认「这就是定案」，需要进 `adr_dir`

## 怎么做

### 1. 写清问题与硬约束

**做**
1. 一句话问题：要决什么。
2. 硬约束：性能/兼容/工期/禁改清单；来源路径可指。
3. 非目标：本次不决什么。
4. 不合格：问题空或只有方案没有问题 → 停。

**做到**：问题、硬约束、非目标齐全。

### 2. 选项与选择

**做**
1. 至少两个可行选项；各写利弊、回滚难度、谁付成本。
2. 记录最终选择与批准人/时间（用户明确确认）。
3. 未确认前文件标 `draft`，不进正式编号。
4. 不合格：单选项强推且无「为何不选另一案」→ 补选项或标待决。

**做到**：≥2 选项 + 已确认选择（或显式待决）。

### 3. 后果与入库

**做**
1. 写后果：得到什么、付出什么、哪些职种/表/接口会踩到。
2. 路径：`.harness/memory/adr/`。
3. 编号命名：`ADR-短名.md`；若替换旧 ADR，旧文件标废弃并链到新文件。
4. 用户确认正文后写入；再 `artifacts-append` 登记。
5. 不合格：未确认就当正式 → 改回 draft。

**做到**：正式 ADR 在 adr_dir；索引已登记；旧条有替代链（若有）。

## 完成检查

- [ ] 问题/选项/选择/后果齐全
- [ ] 用户确认后入库
- [ ] 产物已登记

## 工具锚

- `.harness/memory/adr/`
- ADR 文件命名与交叉链接
- `artifacts-append`

## 失败回哪一步

- 问题不清 → 步骤 1
- 选项不足/未批准 → 步骤 2
- 路径/登记失败 → 步骤 3
