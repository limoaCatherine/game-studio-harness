# CI 冒烟怎么跑

## 何时用

- 提测或合入前要快速验构建可玩
- CI 红灯要分清自动失败还是手工批失败
- 本迭代主改动后要回扫核心稳定路径
- 需要按平台补键鼠/手柄/触控抽测

## 怎么做

### 1. 探测跑什么

1. 找测试入口：仓库测试目录、CI workflow 引用测试的 job、本地一键冒烟脚本；记下实际命令。
2. 读现行 QA 计划的「冒烟范围」节；无则用标准范围（核心稳定 / 变更与回归 / 存档与性能粗看）。
3. 声明模式：完整（sprint）或 quick（quick 须在结果头显式写跳过项）。
4. 探测引擎/测试框架是否在 PATH；未知则记 NOT RUN 原因——NOT RUN≠自动 FAIL，但必须显眼。
5. 输出运行卡三行：命令、范围来源路径、模式。

**做到**：命令、范围、模式可复述；环境探测结论可见。

**不合格**：命令/范围/模式不可复述 → 回本步补探测。

### 2. 跑自动冒烟子集

1. 执行约定冒烟自动集（CI job 或本地等价命令）；保留完整 stdout/stderr 与退出码。
2. 解析：总数/通过/失败；列出失败用例名（最多记 10，超出记数量）。
3. 失败用例保留日志产物上传路径；保持断言与测例原样，用修复或开单处理红灯，不删测装绿。
4. 片状（同命令偶发红）：标 quarantine 候选+重现次数，不计入「已修」。
5. 若框架不在 PATH：记 NOT RUN + 需人工确认来源；结果里显眼标出。

**做到**：自动结果可定位到用例名；退出码非 0 时原因可见。

**不合格**：退出码非 0 无用例名或日志路径 → 回本步补产物指针。

### 3. 手工核心稳定批

1. 冷启到主菜单：记启动耗时与是否崩溃；崩溃即停后续「带伤」叙述，先开缺陷。
2. 新局/继续：能进入可玩状态；主菜单输入响应（按平台）。
3. 基本导航：进设置再返回、开关一次画质或音量，无卡死。
4. 平台输入抽测：按目标平台覆盖键鼠/手柄/触控中与本轨相关的一项。
5. 每项记 通过/失败 + 一句现象；失败写最短复现（≤5 步）；核心失败则整体 FAIL。

**做到**：核心稳定批每项有结果；失败有最短复现；核心失败时整体标 FAIL。

**不合格**：崩溃后仍写「带伤通过」→ 回本步先开缺陷。

### 4. 变更回归与存档粗看

1. 从本迭代变更说明抽出 1～3 条主改动路径，逐步操作到可观察成功。
2. 再跑既有烫手回归点：上次坏过的、缺陷关闭后必回扫的、高风险系统（存档/支付/战斗结算）。
3. 完整模式：存盘→杀进程→读档抽检关键进度；固定场景走 60～120 秒目视尖峰（有帧时计数器则记下）。
4. quick 模式须在结果头显式写跳过项；自动失败与手工同路径合并证据。
5. 变更面为零时仍跑至少一条历史烫手路径；汇总自动+手工：核心稳定任一失败→整体 FAIL；片状保持 quarantine，不装绿。

**做到**：变更面与烫手路径均有结果；完整/quick 模式声明清楚；裁决能区分自动红与手工红。

**不合格**：变更面为零却跳过全部烫手路径 → 回本步至少跑一条历史烫手。

## 做到

- 自动子集有结果或写明未跑原因；失败可定位到用例名
- 核心稳定批已跑；失败有最短复现
- 完整/quick 模式声明清楚；裁决能区分自动红与手工红

## 工具锚

- CI 流水线配置（`.yaml` / workflow）与冒烟命令日志
- 失败用例名与复现步骤写入 `.harness/artifacts/`
- `verify-report.json` 引用本批日志路径

## 失败回哪一步

- 命令/范围/模式不明、框架探测空 → 回步骤 1
- 自动红无用例名、用删测装绿、片状当已修 → 回步骤 2
- 核心稳定崩却继续「整体差不多」 → 回步骤 3（先开缺陷）
- 变更面与烫手路径未跑、完整模式静默跳存档粗看 → 回步骤 4

下一步常接：失败开 `bug-report-write` / `client-bugfix`；阻断盘点见 `build-gate-checklist`。
